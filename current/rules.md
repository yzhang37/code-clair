# 代码编写与审查规则

判断依据是实际语义和已有证据，不是注释行数、空行数、函数长度或语言外观。

<a id="comments"></a>

## 源码注释准则

先读目标函数及必要上下文，独立判断本层是算法、比较规则，还是适配/编排。

本准则约束源码注释。纯注释任务不改可执行代码；用户同时授权日志修改时，日志按本文件的“日志准则”，注释按本节要求分别验收。

输入：`language_list` 为有序语言列表；默认 `[simp_chinese]`，调用方可覆盖，如 `[english, simp_chinese, spanish]`。

1. 在函数入口给一幅可独立理解的总图：要解决什么、决定结果的关系或策略、主要状态如何配合、结论和重要边界。契约与实现概览分开；不要把下游算法写成本层保证。
2. 在读者必须停下来推理的代码旁解释局部状态：非显然常量、跨轮变量、辅助函数的多重更新、关键选择及其理由。说清它们如何维持不变量；不把细节全塞在开头，也不逐句翻译显而易见的操作。不按注释条数评分。
3. 核对正确性：关键选择为何符合规则，状态如何推进、何时停止，局部保证如何合成结果。不要用“不丢不重”冒充选择规则的证明，也不要在未定义全局目标时声称全局最优。
4. 复杂度按关键操作成本 × 执行次数推导，并写清分析范围；区分本层与下游、理论空间与固定容量不足时的失败。不要数循环层数猜大 O。
5. 每项行为须有代码或可信契约依据，区分事实、推测与建议。注释或伪代码本身不能证明实际实现已提供某项行为或保证。交付前遮住代码自测：函数级注释能讲清总图吗？到了难点，附近注释能让人继续推理吗？用边界和反例核对；若实现冲突，报告证据，不把期望的算法写进注释。
6. 有可用名称的函数，函数级说明首句以当前函数名（含括号，如 {@code rehash()}）作主语，使说明脱离相邻代码时仍能明确所述职责和边界属于哪个函数；这种句式不能代替第 1 条要求的总图。
   没有可用函数名时，用实际绑定名或所在接点明确说明对象，不编造名称。
   优先用语言原生、文档工具可识别的格式（Javadoc、Go doc、Python docstring）。对外 API 的参数、返回、异常和副作用按需写实；不凑空洞标签，也不把局部推理全挪进文档注释。
7. 每句独立成组：每个语言行只写该句，按 `language_list` 顺序逐行紧邻写等义版本，再写下一句；函数级与就地注释都如此。待办的公共任务标记不属于任何一种语言的说明，按下方“待实现占位”独立成行且每项只写一次。各语言的具名函数首句均以函数名作主语；Javadoc 组内用 `<br>` 换行、正文组间用 `<p>` 分段，每项 `@param`/`@return` 只保留一个标签，译文放在该标签描述中。
8. 算法之外的业务选择、配置默认值和部署设置也必须解释“为什么”：谁在什么场景使用、要避免哪种实际失败、为何默认这样选、改掉会失去什么能力或增加什么代价，以及适用范围和修改边界。
   不能只把 `DEBUG`、重试次数、缓存开关等配置值翻译成中文，也不能用“最佳实践”代替本项目的业务理由。
   若关键开关容易被调用方或 AI 忘记，应说明为什么把它固化在代码或镜像的默认值，而不依赖每次手动开启。
   理由应写在实际生效的设置旁；较长背景可以链接文档，但不能只留在聊天记录中，也不能只写在远处的总说明中。
   一种环境的理由不能自动套给另一种环境；用户明确指定的用途和默认值，不得被后续维护者以一般惯例为由悄悄改掉。
   按实际选择涉及的条件说明理由，不把使用者、默认值或部署信息凑成每条注释的必填清单。邻近说明已经讲清理由时不重复，也不为补理由编造业务约束。

## 业务说明的具体边界

- 阶段标题必须覆盖下面实际经过的分支，不能把共同接点写成只处理成功。
- 同一接点附近，没有新增条件、行为或理由的同语复述应去重；保留函数总图和必要就地说明，中英等义配对本身不算重复。
  责任已明确移交且没有其他新增信息时，说明接手方负责后，再说明移交方不再负责，也是重复；换主语或换措辞不会增加规则信息。
- 异常路径的执行关系必须写实。实际代码在前一步失败后仍尝试保护处理时，应在该后续处理接点写清执行关系及保护理由，不能写成只在前一步成功后才执行，也不能把尝试写成已经成功或把已有处理写成待实现。
- 区分操作尝试、远端确认与本地记录；点击或提交请求不等于远端已确认完成。
  本地记录失败不能推翻已确认的远端事实；在构造并回传该失败异常的接点，保留已确认对象的身份及当次证据，供上层核对、补记，不能据本地失败改判远端未完成或重新执行。

## 待实现占位

明确留待后续实现的行为，在实际接点使用一个独立成行的 `TODO:` 公共标记；一个标记及紧随的说明只对应一项待办。正常职责边界、普通无操作分支及未证实问题不机械标为待办。

待办按独立实现目标划分；同一目标所需的步骤、触发条件、状态边界和理由属于该任务的说明，不按句数或阶段数增加标记。
是否属于同一目标，须看这些说明与具体待补结果的必要关系，不能只因题材相同或笼统归为一个目标就合并不同任务。

标记语言无关，说明才需要翻译。每句按 `language_list` 顺序逐行紧邻写等义版本，再写下一句；不能让标记混入其中一种语言，也不能随语言重复标记。X 项待办、K 种语言仍只有 X 个标记，每句有 K 种语言版本。

结合必要上下文讲清待补行为、触发条件及当前实现状态；涉及非显然业务选择时，按源码注释准则第 8 条说明理由。格式正确不等于内容完整；不能合并不同任务、删除必要译文或把待实现写成已完成。仅写 pending 不替代可检索标记，只有标记而无具体说明也不合格。TODO 不授权实现待办。

## 日志准则

1. 注释解释实际算法和业务理由，日志用运行值验证预期，两项分别验收。先明确偏差及调查问题，再看实际调用路径；观察输入、已有中间结果和输出、分支操作数、循环推进与停止、异常及异步边界，不按 if 数凑记录或倾倒全量变量。
2. 使用同次操作已经产生的值，不为日志新增查询、远程调用、锁或重复计算；并发变化后的重读值不能冒充当次判断。固定标记只证明到达，未知不能写成成功、失败、零或已确认；stage/reason/next_action 不是必填清单。
3. 只改授权功能及已核实的直接接点，不借日志改变业务、重试、事务、锁、查询或部署。
   既有日志与注释仍按现行标准审查，发现缺陷须报告，保留不代表质量通过；未经授权不得删改，来源未核实先保留并报告。
   对本次任务的全部新增和修改内容负责，不因它已出现在后续快照而免于审查。
4. 日志正文、字段名和代码生成的说明性值使用英文。不记录秘密、完整载荷或不必要个人数据；异常 message、cause、suppressed 也可能回显输入。在负责记录的边界对异常原因及完整异常链作必要脱敏，必要文本限长并转义控制字符；用合成敏感标记检查最终渲染事件和完整异常链。
5. 增加 catch 或跨调用状态前，核实最终记录者、必要上下文和新增诊断价值。已核实上层记录充分时不增加重复包装；仅知道上层有 ERROR 不足以证明证据完整。负责报告的边界应保留当次已知、安全且必要的失败原因，不能只留失败标签。失败步骤、Action 和网页结果可以定位操作，布尔值可以表示失败状态，但都不能代替本地异常的原始原因。依赖日志尚未核实时，应指出已确认的原因缺口，不能据此断言整个系统没有记录，也不能假定上层已充分记录。获授权恢复、补偿或转换另按其职责判断，不因 catch、变量或行数本身判错。
   例如，已确认远端创建、随后本地结果记录失败，且已核实当前边界负责记录时，反例是 `ERROR Posting failed`；正例是 `ERROR Posting result persistence failed action_id=example-action remote_outcome=created linkedin_job_id=123456789 error_code=ECONNRESET`。前者无法区分远端发布失败与本地记录失败；后者关联当次操作和已知远端结果，并用安全原因说明本地失败。示例中的值必须来自当次操作，字段名不是固定模板。
6. 同一事件不逐层刷重复栈；后来独立失败仍须留下可判断重复、持续、影响及结束的证据，不能用“已记录”永久压掉后续故障或把静默当恢复。日志次数不等于故障次数，输出量需要有界。
7. DEBUG 是内部诊断，INFO 是有用的正常进度与结果，WARN 是可行动的退化，ERROR 是重要操作失败或不变量破坏；按被评价操作及实际影响定级。正常资格跳过、配置停发、普通竞争及成功恢复不自动成为错误；进程仍活着不表示本次操作成功。“先写 DEBUG”只是审阅阶段，不能降掉已有重要可见结果。
8. 启动必需数据库不可写、连接或必需表检查失败而无法继续时，必须用 ERROR 说明失败步骤、经必要脱敏的数据库或表等被检查对象标识，以及初始化无法继续的影响。
   检查返回失败时，保留当次已取得的返回值或只读状态等被检查属性；检查本身抛错时，保留安全的异常原因，不臆测它已返回某个判断值。
   短路后未执行的检查明确为未检查，不额外查询或编造值。笼统“启动失败”、仅抛异常或仅 DEBUG 均不能替代这些证据。
9. 调整日志等级时同步调整守卫，不让日志开关控制业务操作。DEBUG 关闭时参数仍可能求值，昂贵取值使用匹配级别的必要守卫；不为可见性开启全部 DEBUG 或把所有细节升级。
10. 正常运行级别保留有界的重要进度、终态及足以缩小故障范围的工作量、阶段耗时和结果。逐候选细节可留 DEBUG，但不能藏掉必要证据。区分排队、连接等待、主动等待、应用和数据库调用时间，检查包含关系；局部次数不冒充全部访问量，未计量不填零，应用 wall time 不证明 SQL 耗时或数据库 CPU，单靠限流也不证明总工作量下降。
11. 分开核实日志发出、有效过滤、输出目的地、采集、入库和检索权限。没搜到记录不证明没输出；工具正文省略不证明应用无日志。WARN/ERROR 不等于已有告警，安静不证明健康；结构化记录与有据可查的解析方式均可，JSON 和固定字段表不是通用前提。
12. 用获授权的正常、偏差和边界输入检查实际输出能否区分原因；模板、编译、覆盖声明和测试数量不替代诊断质量。只做静态审查时说明范围，不能声称生产链路已验收；日志任务不授权生产改配置、采集、部署或重启。
