# Principles

同一份编写质量原则用于检查 rules 正文及其内嵌示例，也用于检查完整 fcase 的必要前提、正反样例、固定预期、理由和边界。只维护这一份，不拆成规则版与 fixture 版，也不另建逐条适用对象标签或映射。检查的是材料的编写质量；反例被正确拒绝仍可使规则通过对应测试。具体编码和注释标准归目标仓库的当前 `rules.md`。

## 共同编写原则

编写质量先看材料帮助读者理解或可靠检验了什么判断关系，是否减少了无谓的拼接与猜测，再看结构与排版。栏目完整、文字精简和正反标签不能代替这种价值。

1. **读完就知道写什么、放哪里。** 说明需要提供的信息及其位置，使写作者能直接行动，审核者也能据同一要求核对；必要判据、事实和关系应自足，不能让读者沿多层链接或凭猜测把它们拼起来。
2. **要求说明因果，不能只模仿形式。** 讲清判断成立的关系和推导；有正面示范时，还须核对它是否在同一目标与必要前提下解决所指问题，并提供或保留本次必须说明的信息，不能只因它比反例少错就视为有用。结果碰巧相同或排版相似，不能替代理由。
3. **正反例把抽象要求变成可理解的差别。** 在可对比的情境中就地解释为什么通过或拒绝。先核对两侧对象、行为、条件和删改信息的对应，以及共同前提约束哪部分；同一题材不等于对照成立。暂不以正反标签、固定预期或作者评价作证，用明确前提与样例支持决定判断的关系，再核对预期与理由；需代作者补想的关系应报告缺口。已取得全文并能确认缺写必需的判断依据时，缺写本身就是编写缺陷，不应仅因此把质量检查记为未完成。
4. **示例服从适用事实和证据。** 判断须与必要事实、实际代码或可信契约一致；区分事实、推测与建议，有冲突就报告，不靠理想结论掩盖反证，也不把规则期望写成实现已有的保证。理由中的事实与因果同样受检，不因位于理由栏就采信或舍弃。材料未提供依据不等于行为或职责不存在；应指出具体缺口，不能据此把相关信息当作赘述删掉。
5. **边界阻止机械照搬。** 讲明必要前提、例外和适用范围，不按编号、文件身份、词语、题材、函数名、产品名或外观套用结论。仅用于定位的信息改变，不改变依据相同的判断；前提、事实或说明改变时，应重新核对。名称实际影响行为或适用范围时，仍须按其含义判断；删减文字不能删掉决定判断的条件。
6. **示例解释判据，不承担外部案例目录的职责。** 按解释需要选例，不与外部 fixtures 逐项登记或按固定数量补齐；新增 fixture 不要求规则中的示例跟着增加，完整材料也不能靠另一份案例补齐含义。

简单材料能清楚显露或稳定检验既定判据，也有解释或检验价值，不要求每例新增知识、补出完整实现或增加业务复杂度。不是本例检验对象、且已明确给定的共同约定，可以作为前提，不必另证其优越性或各配反例；共同约定不能代替对本次受检关系的核对。

下述教学对照展示这些原则的作用；具体题材、算法、语言和排版不构成固定模板或必须收录的内容。核对原则时保留其原因，不能只留下指向示例的快捷方式。

## 运用原则的复核对照

- 复核反例：只因一个文件过去被拒绝，就拒绝已经补足前提的修订稿；或只因换了编号，就接受仍有同一缺口的材料。结论取决于材料身份，没有核对决定判断的依据。
- 复核正例：原材料未说明失败是否也进入清理阶段，缺少核对标题“成功后清理”适用范围的必要依据；修订稿补充了失败也进入该阶段的前提，应据此重新检查标题是否遗漏失败路径；补足前提也不代表标题或其他要求已经通过。

## 职责与信息组织

`rules.md` 是编写和审查代码共用的自包含标准，可直接用于 AI 辅助 skills 和以“一次性写出正确代码”为目标的 prompts，不改成只供事后审查的手册或多层文档导航。必要要求和适用边界在正文完整、精炼地表达；内嵌正反例的必要前提、理由和边界也就地讲清。代码编写与审查使用完整 rules、目标代码和必要事实，不读取外部 fixtures 补标准，也不接受外部 fixture 文件作为代码问题的规则引用。移去 fixture 访问就失去的代码判据，是 rules 的缺口。

`cases/` 是检验 rules 是否漂移的 fixtures；每个 fcase 独立写清检查目标、必要前提、正反样例、固定预期、判断理由和边界，不通过链接、文件名、编号或“另见其他案例”介绍其他 fcase 的职责或补齐自身说明。规则和外部证据链接只用于定位支持材料，不能代替必要说明。单个 fcase 只检验同一类失败原因，其他相关前提保持一致；不以额外问题替代该样例既定的拒绝原因。

固定预期不由当前 rules 的输出决定。同一次验收期间，固定预期、理由、前提和边界保持固定并一并核对，不能修改反例或预期来迁就 rules；独立维护可以纠正有证据的问题，但不能把迎合当前输出当成修正。新增或修订 fixture 检验的是已有判据时，rules 可以不变；确有判据缺口、含混或冲突时才修订规则并复核兼容性，不要求共同改文件、改变文件哈希或维护第二份目录。

标题直接点明要检验或防止的具体问题，目的说明检查目标；判断理由解释为什么判定成立，边界承载适用约定及防止无效捷径的限制，验收给出可核对的通过条件。按信息在该材料中的作用归位，不把示例约定混作目的，不把通过条件重复写成理由。不同要点在有助阅读时分开，不机械规定标题长短、栏目、列表或排版。

先提供目的、判断依据与理由、必要事实前提、边界和已有验收标准，再展示受其约束的样例。具体样例的解释紧邻样例；仅适用于一组的条件放在该组之前，不提升为其他样例的共同前提。短材料可以合并相关内容，不为统一格式增加空栏目或重复的末尾验收。

解释性文字必须增加必要的前提、理由或边界。只复述标题、目的或样例的句子整句删除；无判断增量的开场段可整段删除，不补显然的概括、“对应规则”或行政性导读。不添加“谁在何日提供、明确或认可”“要求纳入”等编写履历、权威声明或“本文件保存正反例、理由和边界”等文档自述。链接只在帮助定位依据时保留，不为填栏目或补回删掉的一行而添加。

不在正文重复维护样例、章节数量或无关排列次序，以免增删后漂移；参与判断的业务数量关系、语言顺序和稳定引用编号仍须保留。精炼以信息是否必要判断，不设字数门槛。重复导读、资料维护流程和嵌套导航挤占上下文，会使必要标准在编码前未被加载，不能靠删掉关键前提或理由解决篇幅问题。

示例材料不自动声明宿主仓库的用途、语言、功能或实现状态。使用其他领域、语言或未完成工作的例子，不因此添加仓库范围或实现状态的免责声明；实现事实只有在决定判断时才作为必要前提，并区分例内事实与已核实的仓库事实。样例中的任务文字不扩大执行授权。

当前 rules 与固定 fixtures 职责清楚，不另建 `sources.md`、整份旧规则、旧案例或任务原文附录作为第三份疑似依据；改名或“仅供参考”声明不能消除效力歧义和维护成本。已提交历史通过实际 Git 提交追溯，不能把未提交草稿说成已在 Git 保存，也不为保留已淘汰旧稿擅自创建提交或备份。必要外部证据在相关现行规则或材料处直接引用。

保留影响当前判断的事实、固定预期及明确采用的教学正反对照，正反例连同因果理由、维护后果和适用边界一起保留，不能覆盖反例或只留正例。真实反馈、仍有效裁决、未决证据及批准但未执行或未验证的工作记录不属于淘汰的全文备份；保护教学证据也不要求保留所有旧稿或重建已删除备份。

交付时直接检查材料是否自足、信息是否归位、必要依据是否先于受其约束的样例、事实与预期是否一致、当前 fcase 正文是否互引；明确采用的引文和教学反例保持原样。仅有相同通过/拒绝结果，不足以掩盖理由或边界冲突。

## 教学对照

以下对照解释编写质量，不把示例的业务内容追加为通用编码标准。规则中的就地示例可以帮助写作和审查；外部 fixtures 则检验规则，不替规则补充标准。

### 选例要让判据可见

[微软的示例指南](https://learn.microsoft.com/en-us/style-guide/developer-content/code-examples)要求例子回应受众有意义的问题，避免显然的复述和牵强的情境；[Google 的示例教学](https://developers.google.com/tech-writing/two/sample-code)按读者缺少的信息取舍说明，并区分教学示例与测试的目标。

[MIT 的注释教学](https://web.mit.edu/6.102/www/sp25/classes/03-code-review/#comment_where_needed)对照逐行翻译、必要假设及阶段目的，并进一步用好命名的函数表达阶段结构；用途、契约、非显然步骤和理由都可能增加理解，不能只按是否写“为什么”评分。[Amazon 的例子](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)用“相同参数也可能是两次有意创建”显露判断缺口；[CMU 的契约教学](https://www.cs.cmu.edu/~15122/handouts/lectures/01-contracts.pdf)让断言得到前提、契约或推导支持。采用的是让依据可见的选例方法，不是这些来源各自的编码规定。

- 编写反例：给两段未说明含义与对应关系的表述贴上正反标签，只称后者“更准确”，再以目的、理由、边界齐全证明材料合格。读者仍无法核对决定结论的差别；补齐栏目没有补足依据。
- 编写正例：限定在 Bash，展示 `s="text"` 与 `s = "text"`，说明前者是赋值，后者按命令解析。只有空格变化，却改变了行为，能检验常见误用；语言、输入和决定判断的差别都可直接核对。

这里检验的是材料是否显露判据，不以题材、例子大小、机构名称或解释句数评分。若邻近材料已经使差别清楚，简短结论可以足够。正反标签可记录固定预期，不要求重复填写布尔字段；预期记录与其成立的依据应分别核对。

### 编写对照：把项目内改词讲成可理解的案例

案例应让读者知道检查什么、根据什么判断，以及正反差别为什么重要。
把单句注释改得更准确不足以说明整份案例已经讲清这些关系。
以下引文保留原有片段及其预期，用来展示讲解需要交代的内容；不能由片段的正反标签直接决定整份材料的编写质量。

````markdown
# 注释标题不能把共同处理写成只处理成功

## 目的

检查阶段标题是否如实概括共同处理接点，避免读者误以为这里只处理成功结果。

## 判断理由

阶段标题决定读者对后续处理范围的预期。多个结果分支共用同一接点时，标题若只概括成功分支，就会隐藏其他实际经过的路径，使读者错误理解代码的职责范围。

## 边界

适用条件是 `recordResult()` 同时处理已创建、未提交、平台拒绝及证据不足的结果。

## 验收

- 标题能够涵盖给定前提中的各类执行结果，不把共同接点限定成只有成功后才执行的步骤。

## 反例

```cpp
// 4. 写入「已提交」后交接。
// 4. Hand off after recording confirmed submission.
```

把共同接点写成写入“已提交”后才交接，遗漏了其他实际经过的结果。

## 正例

```cpp
// 4. 记录本次执行结果。
// 4. Record this attempt's outcome.
```

“本次执行结果”覆盖共同接点的各类结果，没有把处理范围限为成功分支。
````

引文已给出多种结果共用这一阶段的前提，能够支持标题范围的比较。
补写可以把读者需要从“遗漏”“覆盖”中推导的具体关系就地展开，说明未提交路径会怎样被误读；是否已经讲清，应按关系是否可理解判断，不以有没有重复某个词句为标准。

#### 编写时应讲清什么、放在哪里

1. **让例子承担明确的教学任务。** 在目的中写出读者要学会的判断，在邻近讲解中解释这种差别为什么重要。
   本例可以教会读者发现标题把处理范围说窄的问题，不能仅凭改词更准确就宣称讲解充分，也不能只因标题接近函数名就认定它多余。
   若还要示范该标题应当保留，就须说明它相对函数名和邻近结构补充了什么理解；已有结构足够清楚时，不增加重复注释。只检验范围的对照，不据此推定标题必须保留。
2. **把业务词语转成可核对的关系。** 将决定判断的前提放在本组样例之前，在对照旁说明哪些路径会被误解。
   例如，本例可展开“未提交也进入本段，却被‘已提交后’的标题排除”的冲突；邻近前提已经使关系清楚时，无须重复同一句话。不能未经说明把“已提交”等同于“成功”。
3. **解释改写解决了什么，并保留结论边界。** 紧邻样例说明读者会误认哪些处理路径，以及正例如何修正这种理解。
   本例的范围修正已有前提支持；若还声称改写完整保留原职责，就须补明“交接”信息由何处承载，不能凭正反标签补证，也不能把缺少依据当作删除职责说明的理由。

#### 编写正例：补出能直接核对的讲解

```text
检查目标：概括整个结果记录阶段的标题，是否把处理范围写窄。
必要前提：确认未提交的结果也会进入这一阶段；标题统领整个阶段。
反例：“写入‘已提交’后交接。”
正例：“记录本次执行结果。”
判断理由：未提交时仍会在这里记录，反例却让读者以为这一步只发生在已提交之后，容易漏看未提交结果的记录位置。正例去掉了这一限制。
结论边界：这段对照说明标题范围得到修正；“交接”职责是否完整保留，还需相应依据。
```

这段补写把必要前提放在样例前，把具体差别、误解及其影响放在紧邻的理由中，并说明结论能够支持到哪里。
简单对照只要能显露判断关系就可以成立，无须补造完整实现或增加业务复杂度；材料缺少本次必需的依据时，应指出所缺关系，不能按题材或旧评价固定拒绝。

### 自包含标准、目录与检验方向

- 反例：正文只说“多语言 TODO 见案例 0001”，再让读者从其他案例寻找边界。写代码前没有拿到完整要求，规则也变成了导航入口。
- 正例：正文直接规定“每项待办只有一个独立成行的公共 TODO 标记；各语言说明按规定顺序逐句等义配对”，并写明不能靠合并任务或删译文达标。条文本身能指导写法，fixtures 再检验这些条文是否保持原有判断。

另列一份案例目录会让新增案例需要两处同步，漏加快捷方式还会被误当成规则尚未纳入该案例，增加无意义的维护成本。

- 反例：每增加一个 case，就要求在 rules 追加链接并修改规则文件；没有同时改动就拒绝进入验收。案例是否存在被错误地绑定到第二份目录是否更新。
- 正例：新增案例检验已有规则，规则正文不变，照常核对固定预期；只有发现实际判据缺口或冲突时才修订条款并复核，不维护另一份案例目录。

外部 fixtures 若替 rules 提供未写出的代码标准，就把检验规则变成补充规则，掩盖 rules 漏写判据的问题。

- 反例：审代码时从 rules 跳到外部 fixture 寻找额外判据，或直接把 fixture 文件当作规则引用；离开 fixtures 就无法按同一标准判断。
- 正例：规则验收用 fixtures 检验 rules；代码编写与审查只应用完整 rules 和必要事实，继承仍适用的人的裁决。fixtures 验收结果说明规则经过了什么检查，不增加代码准则。

下列写法在右列所述条件下构成反例；维护时应避免恢复这些职责混淆，而不是把其中的词语列成禁词：

| 反例写法 | 为什么错误 |
| --- | --- |
| 开头写“本文件与 `cases/` 共同构成当前审核依据” | 把检验规则的 fixtures 变成了另一套代码准则 |
| 在 rules 中编排 case 写法、“同步修订规则及其对应关系”和逐 case 验收流程 | 混入资料维护职责，不能直接指导代码编写或审查，还强迫两份资料同步变化 |
| 正文写“标记组织见案例 0001”等导航 | 把规则变成 fixture 导航，增加跳转和维护负担；必要判据应在正文说全 |
| 末尾维护“Fixtures 对应关系”及逐项链接 | 重复维护案例目录，新增案例又要更新另一份清单 |

这些反例不禁止 rules 内嵌教学案例。例如，前提是外部结果尚未确认、按约定保留预留名额，且邻近尚未解释理由：只写“保留预留名额”是反例；写“保留预留名额，避免把可能仍被占用的名额误算为空闲”是正例。前者复述动作，后者解释风险；理由必须有业务依据，邻近已讲清时不重复。这样的对照直接帮助写注释和审查说明是否充分，可以放在规则正文中，无需链接或对应 fixture 编号；引用其中内容时，规则位置仍是 rules 本身。

以下对照说明案例的写法，不改变其中代码片段的业务审核预期。维护编写要求时，同时保留正反例原文、判定理由、维护后果及适用边界；不能覆盖反例，也不能只留正例让后续模型猜标准。

### 开场说明的编写反例

```markdown
# 多语言 TODO：一项待办共用一个独立标记

来源：仓库所有者于 2026-11-17 在当前任务中直接提供，并要求纳入。对应规则见 [rules.md 的“待实现占位”](../rules.md#待实现占位)。本文件同时保存这一案例的正反例、判断理由和适用边界。

## 背景与适用范围

本案例检验 X 项待办、K 种语言仍只有 X 个任务标记，不能因翻译变成 X × K 个。示例的语言顺序为中文、英文；其他语言组合遵守其规定的 `language_list` 顺序。`cpp` 是展示语法，不限定目标仓库的实现语言。

以下三段表达同一项账本接入待办，说明正文相同，只改变任务标记的位置或次数；不表示真实账本已经接入。

本案例只约束任务标记与多语言组织。业务理由是否清楚见[案例 0007](<0007. business-choice-rationale.md>)，当前实现状态是否写实见[案例 0008](<0008. todo-implementation-status.md>)；不同失败原因不并入本案例的反例。
```

标题概括了要求采用的写法，开场又先交代编写过程、导航和收录内容；读者需要的问题与目的没有直接呈现。检验目标和语言顺序应清楚表达；“cpp 不限定目标仓库语言”不影响本例判断，应删除。

其中“以下三段”还重复维护了样例数量；整句对比说明在检验目的和样例已经明确的前提下没有判断增量，末尾又把案例材料当成仓库实现声明来防范。应整句删除，而不是改成不带数量的导读。

介绍其他 cases 检查什么的互引段也应删除。本例目的已经定义检查范围；其他案例各自在自己的目的中说明检查什么，无需在这里重复维护它们的分工。

### 四个章节的职责：完整正反对照

#### 目的

检查案例的目的、判断理由、边界和验收是否职责清楚、信息归位，避免同一条判断信息散落多处，导致读者难以理解、修改时遗漏或漂移。

#### 判断理由

每个章节承担不同的阅读任务。目的让读者知道检查什么，理由解释判定的因果关系，边界给出必要约定和不能破坏的前提，验收提供可核对的通过条件。信息各有归属，修改约定、理由或标准时就能找到对应位置，不必在多个章节反复同步同义表述。

| 章节 | 反例的问题 | 正例为什么更好 |
| --- | --- | --- |
| 目的 | 混入数量标准和语言约定，读者难以分清目标与给定条件 | 直接说明要检查的标记组织问题及要避免的错误 |
| 判断理由 | 解释因果后又复述 X/K 标准，需要和验收同时维护 | 解释“译文增加没有增加任务，因此标记不应增加”的因果关系，不重复列标准 |
| 边界 | 混入整体审核结论和执行授权，增加本例判断不需要的说明 | 保留语言约定及不能靠合并任务、删除说明来通过检查的限制 |
| 验收 | 混合通过条件、样例编号及其他检查范围的说明 | 用独立可核对的条件表达通过标准，增删样例不要求同步改写其数量或位置 |

#### 边界

- 这组材料判断的是案例写法。四个标题和原有 TODO 检查目标保持一致，不能靠改变业务判断或删掉必要前提让改稿显得更清楚。
- 不以字数、段落数量、是否分点或是否像正例排版来判定好坏，也不要求所有短案例增加空栏目。
- 在这组材料中，语言顺序是给定约定，放在边界；X/K 关系是通过条件，放在验收。归属取决于信息在具体案例中的作用，不能推导成“某个词永远只能放某一节”或“任何数字只能出现一次”。
- 必要的业务数量、任务身份、说明内容和判断边界必须保留；删除重复表达不等于删除这些判断依据。

#### 验收

逐条核对文字承担的作用及其归属：目的能独立说明检查目标；理由能解释为什么采用这些判断；必要约定和限制明确；通过条件可直接核对。能指出反例具体哪里混写、如何造成多处维护，并解释正例如何解决，而不只说“更简洁”。每次修订编写规则时，按这组固定正反预期及理由复核，不得把反例改成正例来迎合新规则。

#### 编写反例

```markdown
## 目的

- 本案例检验 X 项待办、K 种语言仍只有 X 个任务标记，不能因翻译变成 X × K 个。
- 示例的语言顺序为中文、英文；其他语言组合遵守其规定的 `language_list` 顺序。

## 判断理由

TODO 是语言无关的任务标记，说明文字才需要翻译。标记单独成行，使各语言说明采用相同结构；一项待办只保留一个公共标记，避免按标记检索和计数时重复。

因此，X 项待办、K 种语言，应有 X 个任务标记；每项说明中的每句分别提供 K 种语言版本，按规定顺序逐行紧邻配对，再写下一句。

## 边界

- 不能为减少标记合并不同待办、删除译文或删减已有说明，也不能只删除英文标记而退回反例一。
- 标记格式通过不等于其他规则也通过；其他规则的问题须按各自依据报告。
- 示例不授权实现账本、改变业务行为或扩大源码修改范围。

## 验收

逐项确认一项待办只有一个独立的公共标记，各语言说明逐句紧邻对应，任务数不随语言数增加。反例一因标记位置被拒绝，反例二因标记随语言重复被拒绝，不以缺少业务理由或实现状态代替本案例的拒绝原因。
```

这段文字把数量标准和语言约定放进目的，在判断理由中再次列标准，边界又混入不参与本例判断的整体审核、执行权限说明。数量关系和语言组织分散在多个章节，同一次变更需要多处同步；漏改时，章节之间就可能出现不同说法。拒绝的是这种职责混淆和重复维护，不是其中的 TODO 标记原则。

#### 编写正例

```text
目的
检查多语言 TODO 的标记组织，避免同一待办被重复标记，并保持各语言说明逐句对应。
判断理由
TODO 标识的是待办任务。增加译文没有增加任务，因此不应增加任务标记。

公共标记独立成行，可以避免它依附于某一种语言的说明；各语言逐句对应，便于核对它们是否表达相同内容。
边界
- 本例说明按每句中文、英文的顺序排列。
- 不能把不同待办合并成一项来减少标记。
- 不能通过删除译文或删减已有说明来满足标记要求。
验收
- 每项待办恰好对应一个独立成行的 TODO 标记。X 项待办、K 种语言，仍只有 X 个标记。
- 每句说明均按规定的语言顺序提供等义版本，紧邻排列后再写下一句。
```

这段文字保留了检查目标和必要约束，同时明确各节职责：目的说明问题，理由解释因果，边界承载本例约定和防止规避的限制，验收集中表达可核对条件。语言约定改变时修改约定，标准改变时修改验收，理由改变时修改因果说明，不必在几个章节反复维护同义副本。

### 规则与 fixtures 的职责：完整正反对照

#### 目的

保持当前规则与固定案例的职责清楚，避免整份历史副本成为读者或模型需要辨别效力的第三份疑似依据。

#### 判断理由

`rules.md` 表达当前编写与审查标准；`cases/` 用具体正反例、固定预期和理由检验规则是否漂移，不为代码审核补标准。把旧规则和旧案例全文再次复制到当前资料目录，只增加一份需要辨别当前效力的旧材料，并未因此承担当前规则维护或固定预期校验的职责，不能代替其中任何一方。

历史副本即使声明“不是规则，也不是 fixture”，读者仍要辨别它与新版的关系。文字更完整、名称叫“来源”或标注“完整保留”，都不能赋予它当前效力。保存旧文字不能代替维护当前规则和验证固定预期，也不能消除版本分歧的辨别成本。

#### 边界

- 历史版本通过实际 Git 提交追溯。未提交的草稿不会自动进入 Git 历史，不能声称删除前它已被 Git 保存；也不为保留被明确淘汰的旧稿擅自创建提交或另一份备份。
- 明确采用的教学正反例及其判定理由属于有效教学材料，继续保留；它们与无当前用途的整份旧规则、旧案例或任务原文副本不同。
- 必要外部证据在相关现行规则或案例处直接引用。真实反馈、仍有效的裁决、未决证据和批准但未执行或未验证的工作记录不属于本次淘汰的全文备份。
- 删除历史副本不能改变当前规则的实质含义、固定案例的预期或仍有效的适用条件，也不能把反例改成正例。问题是重复依据的职责冲突，不能仅靠改文件名或添加免责声明解决。

#### 验收

当前资料清楚区分现行规则与固定案例；不存在另存整份旧规则、旧案例或任务原文的第三份疑似依据。模板、整理指令和资料说明不再要求恢复这些副本。当前案例和有效教学对照的事实、固定预期、判定理由及边界完整保留，历史追溯不冒充未实际发生的 Git 提交。

#### 编写反例

```text
current/
├── rules.md               当前规则
├── cases/
│   ├── 0001. multilingual-todo.md       新版案例
│   └── 0001. multilingual-todo-old.md   整份旧版副本
└── sources.md             整份旧规则和旧案例，再声明“不是规则，也不是 fixture”
```

这个安排把规则和 fixtures 的旧版本继续摆在当前目录。读者需要区分旧副本和新版；旧案例副本放在现行案例目录中，还增加了把旧稿误当有效 fixture 的风险。额外的“仅供追溯”声明没有承担当前规则维护或固定预期验证的职责，反而增加了材料效力不清和误用旧版本的机会。

#### 编写正例

```text
current/
├── rules.md    当前判定规则
└── cases/      当前正反例、固定预期、理由和边界
```

当前工作树清楚区分现行代码标准与检验它的 fixtures，历史版本通过实际 Git 提交追溯。明确采用的写法正反对照与判定理由保留在编写规范中，供后续模型理解标准；不再复制整份旧稿来代替这种教学，也不要求读者在几套全文之间判断哪个版本有效。
