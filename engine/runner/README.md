# 本地审核器运行说明

本目录是 `engine/` 的执行程序，使用 Python 标准库及独立 Codex CLI；目标仓库不因此改变技术栈。当前提供代码审核、独立材料质量检查、固定案例回归、组合材料维护、回应保存及 commit-msg，Pi 尚未接入。对象与职责见 [Engine 审核模型](../README.md)，编写质量统一使用 [Principles](../principles.md)，执行流程见 [workflow.md](../workflow.md)。

## 已确认要求与当前实现

下表对应 engine 模型中的工作关系，集中说明现有入口及实现边界。

| 工作 | 现有调用方式 | 实现边界 |
| --- | --- | --- |
| 按 rules 审查代码 | `make review`、`make review-staged`，以及显式启用后的 commit-msg | 审核所选 Git 快照；rules 指导编写的用途不表示这些入口会生成代码 |
| 检查 rules 的编写质量 | `make review-rules-quality`；普通代码审核另有健康阶段 | 独立入口用 `check_materials` 按同一份 Principles 检查工作树完整 rules 及内嵌示例 |
| 检查完整 fcase 的编写质量 | `make review-fixtures-quality`；普通代码审核另有健康阶段 | 与上一项共用 `check_materials` 和唯一 Principles；检查完整 fcase，不加载产品 rules，不要求反例符合 rules |
| 用固定 fixtures 验收 rules | `make review-rules`；普通审核另有带预期的兼容性核对 | 独立入口读取工作树，先隐藏答案判定片段，再核对理由和边界；两种核对分别留账 |
| 组织审核、维护材料、保存回应与整理经验 | `make review-engine`、`make review-respond`、`make review-engine-respond`，以及现有代码 review 流程 | `review-engine` 调用 `maintain`，依次组合两项质量检查与固定回归，只维护工作树材料；两类回应分开保存。自动 learn 候选整理和正式知识写回未实现 |

提交处置统一按 [共同工作流](../workflow.md#审核结果与提交决定) 的要求：reviewer 只负责审核和报告，Git hook 默认按结果阻止未通过的提交；提交者明确要求本次跳过时，将其说明、已发现问题及未修复或未完成状态写入本次 commit message 后放行。问题新旧不限，理由无需 AI 批准，跳过不改变审核结果，不另建账本或许可管理机制。

[commit-msg](commit-msg) 是 Shell hook，本次跳过的读取、提交说明写回和放行逻辑均在此 hook 中，复用 Python reviewer 的审核结果。没有本次跳过指令时，沿用 reviewer 的退出码；有明确说明时，记录全部已知问题或审核未完成状态后返回成功。日期、提交者和对应提交内容由 Git 自身提交记录追溯。

## 安装与入口

本节 Make 命令在安装后的宿主根目录运行。原厂仓库直接使用根 `engine/`，宿主才使用 `.clarity/engine/`；软件安装、Git 更新和生成 Make 入口见[安装说明](../../README.md#installation-and-updates)。原厂根 Makefile 只负责离线测试。

需要 Python 3.10+、有已跟踪代码的 Git 仓库和可用的独立 Codex CLI；配置未指定模型时使用 CLI 默认。API key/auth.json 认证适配已有，只有系统钥匙串的方式仍未验证。软件可安装或更新到没有 Git 的目录，但不会初始化 Git；代码审核在这种目录明确报告需要 Git 仓库和已跟踪代码。

安装和更新都会生成 `.clarity/Makefile`，并在宿主实际生效的 Makefile 加入入口；没有宿主 Makefile 时创建它。已有正文及默认构建目标保留，拒绝覆盖外来同名目标或被修改的托管块。是否选择 Git tracking 只决定自动暂存，不决定能否运行 Make 入口；默认 no 保留原有索引。

首次使用只需填好宿主自己的 `.clarity/current/rules.md`，然后运行：

```sh
make review
```

项目实际准则由所有者提供，安装器不会代写。缺失、空白或与本版初始底稿相同的 rules 会明确拒绝，提示填写 `.clarity/current/rules.md` 后重新运行。初次建立本机依据时，与同版底稿相同的 `.clarity/current/cases/case.md` 不作为正式 fixture；没有其他案例时保留 `no_coverage`，已有正式规则仍可用于代码审核，不把没有覆盖说成 fixtures 验收通过。

首次 `make review` 或 `make review-staged` 在配置缺失时调用 `prepare_review()`，在审核锁内建立配置和运行引擎快照，不安装 hook。已有配置原样保留，不重新采用资料或重置自定义模型参数。新配置默认选择 `.clarity/current/rules.md` 和 `.clarity/current/cases/`，使用 Codex CLI 默认模型、两个首审及每次调用 600 秒上限。

新建配置时，若 HEAD 中没有任何所选依据资料，保存首次使用的本机原文为 `basis_snapshot`，并记录 `basis_source=local`；不要求先将 `.clarity/current/` 加入 Git。该配置绑定采用时的工作树，保存正文、模式及 SHA-256 标识；本机标识不是 Git 对象。之后冻结本次本机资料，与已保存的采用原文配对；新增或修订内容作为候选，不因重新运行审核或启用 hook 自动成为正式依据。未填案例底稿的排除按配置中保存的底稿哈希判断；填写后进入候选集合。审核输入标识包含本机资料，结束时重新读取资料、配置和仓库身份核对，变化时报告未完成。

若 HEAD 已含所选依据，新配置继续使用 Git 依据路径。旧配置也保持原有 Git 语义：按固定基线与当前 Git 快照的路径并集展开选择，以基线或已采用原文哈希确定正式版本；之后加案例不必逐个重装，删除与空白材料也不从本次选择中悄悄消失。软件升级保留既有配置、规则采用哈希及本机采用原文，只更新运行引擎摘要，不借升级重新采用依据。

显式 `--basis` 仍可选目标仓库的自定义规则位置，但不能把 `.clarity/engine/` 内的元文档、提示词或程序选为产品依据；选文件或展开目录均拒绝，既有配置在运行时也检查这一边界。该限制按引擎位置识别，不禁止其他目录中的同名文件。

日常代码审核入口：

```sh
make review
make review-staged
```

前者读取 HEAD，需要已有提交；后者读取暂存区，可在首次提交前检查已暂存的代码。二者都不创建提交，代码对象始终来自所选 Git 快照，本机依据模式也不会把未跟踪或未暂存的业务代码加入审核对象。这两个 Make 入口执行源树中的 runner，并从同一源树加载模型、Principles、流程和提示词；其引擎摘要必须与配置相符，否则报告未完成。

如需 Git 或 SourceTree 提交时自动审核，再显式启用可选 hook：

```sh
make review-install
```

此入口共用首次准备逻辑，缺配置时建立配置，已有配置时保留原参数与采用依据；随后安装自己的 commit-msg、移除自己的旧 pre-commit，不覆盖外来 hook，不改当前资料或未填底稿，也不运行语义审核。它不是软件更新入口；宿主用 `./.clarity/update` 同步程序、已有运行快照及自己的 hook。

运行引擎复制到 Git common dir 并绑定版本，包括模型正文、唯一 Principles、流程、全部共享 Markdown 提示词及安装清单中的 runner 模块。已有快照不会随源文件编辑自动更新。普通仓库通常使用 `.git/clarity/`，worktree 由 Git 决定控制目录。commit-msg 执行该运行快照，读取 Git 实际索引，包括 Git 传入的 GIT_INDEX_FILE，保持部分提交和未暂存修改的边界。直接调用 Python 审核安装器仍会安装 pre-commit，不等于上述可选 commit-msg 入口。源码、运行快照及某次审核实际使用的版本须分别核对；源码或文档存在不表示实际语义审核已经执行或通过。

下述独立材料检查和组合维护由 Make 调用源工作树的 runner，读取工作树材料，不要求安装引擎摘要匹配。它们只复用配置中的 Codex 可执行文件、模型和调用上限；没有配置时使用 `codex`、CLI 默认模型和 300 秒上限。它们固定使用 `.clarity/current/rules.md` 与 `.clarity/current/cases/`，不沿用代码审核的自定义 `--basis`。独立入口可在安装前运行，但不能据此认为代码入口或 hook 已刷新。

显式启用 hook 后，在 SourceTree 中正常暂存文件、填写提交说明、点击提交即可触发。审核未通过时，SourceTree 的提交错误结果中会显示 hook 输出。若仍要提交，在提交说明另起一行填写：

```text
Review-Bypass: 这里填写你的一句话说明。
```

再次提交时仍执行审核；该行只覆盖审核结果对本次提交的阻止，不跳过审核、不缩小范围，也不要求 AI 认可说明。hook 将完整问题清单或未完成状态写进本次 commit message 后放行，不新增独立理由记录。这个界面使用 SourceTree 自己的提交错误展示，不另建警告窗或审批界面。

## 独立材料编写质量检查

```sh
make review-rules-quality
make review-fixtures-quality
```

分别对应 `review.py check-rules-quality` 和 `review.py check-fixtures-quality`，均支持 `--repo`、`--config`。二者共用 [material_check.py](material_check.py) 的 `check_materials`，显式加载源引擎模型、唯一 `principles.md` 及同一份 `material-check.md` 提示词；没有另一套规则版或 fixture 版 Principles。

rules 检查读取完整规则正文和内嵌示例；fixtures 检查递归读取 cases 下全部 Markdown 的完整 fcase，包括前提、正反样例、GOLD、理由和边界，不加载产品 rules。后者检查这些材料本身写得是否清楚、自足，不判断样例应否被产品 rules 接受，也不要求反例变成正例。缺失、空白、不支持的资料或没有完整 fcase 均报告未完成，不凭空集合通过；材料总量超过 1.5 MB 时不截断。

每份完整材料逐一交给模型，按连续正文行段记录覆盖证据、材料与 Principles 原文引用和理由；行段仅用于核对覆盖，不作为清晰度评分。工具先保留有效发现，再核对全部覆盖；模型输出或后续阶段未完成时，已保留发现仍在结果中，其余材料明确区分未运行。结束时重读材料、源引擎和配置，变化会使本次未完成。

退出码 0 表示全部完整材料质量检查通过，1 表示有已引用原文的编写质量问题，2 表示取材、调用、引用、覆盖或输入一致性不足。结果分别写入 Git 控制目录的 `clarity/material-checks/rules/run-*/`、`clarity/material-checks/fixtures/run-*/`，独立指针为 `latest-quality-rules.json`、`latest-quality-fixtures.json`。按取材与调用进度保存 `input.json`、`result.json`、`report.md` 及模型原始记录；不覆盖代码审核的 `latest.json`，不改材料、索引或安装配置。质量通过不代替固定案例回归或代码审核。

## 独立固定案例回归

```sh
make review-rules
```

对应入口是 `python3 .clarity/engine/runner/review.py check-rules`，也支持现有的 `--repo` 和 `--config` 参数。它读取工作树里的当前规则及全部案例，与 HEAD、暂存区和安装时采用的旧正文区分；只复用本地配置中的模型入口与调用上限，不要求先重新安装 hook。

工具保持 cases 原样，先从明确正反区段取出独立代码块或 blockquote，给每个片段一个不暴露类别的标识。正反标签按标题开头的“正例”或“反例”及其可选序号、冒号说明识别；说明中提及另一类标签不改变本区段预期。普通标题仅含“判定”“标准”等词不会因此屏蔽前提；明确的理由、验收、来源等栏目不进入盲判。被测模型每次只收到完整规则、一个片段及 `context` 中声明的检查目标和事实前提，不收到预期答案、案例标题、来源或判定理由，也不注入 Principles 作为追加判据。“目的”正文标为检查目标，只限定受检关系，不追加代码标准；目标混入正反标签或固定预期时报告未完成。例内前提不等于已核实宿主仓库实现，待判注释也不能自证行为。

前提从适用的中性区段按句摘录，识别“适用条件是”“本例中”“本例中的”“本例给出的是”“当前”“下列注释均位于”等明确事实声明、语言约定、异常观察、依赖日志未核实状态，以及“如果已核实”的条件；不再截断同段后续接点句。共同前言用于全组，组内前言只用于该组后代，正反区段、理由、验收及历史原文不参与摘录。规范性约束不作为事实整段发送；候选前提混入明确标签或固定预期时报告未完成。此取材只支持明确声明的句式，不保证理解任意自然语言；必要事实缺失或独立片段形式不支持时报告未完成，不补造事实或自动改 case。

全部片段独立判定后，由工具比较固定正反预期。只有标签全部正确，才在新的隔离调用中逐案例复核已有理由及适用边界；复核者可以看完整案例，但仍只用 rules 核对判定，无权修改独立判定或固定预期，不能把错判改成通过。普通项目源码、历史来源正文、Principles 和旧 review 提示词不参与此入口的判别输入；规则自身保留完整原文。

退出码 0 表示全部固定预期与理由边界均通过，1 表示有错判或理由不符，2 表示材料、调用、覆盖、引用或输入一致性不足。结果写到 Git 控制目录的 `clarity/rules-checks/run-*/` 及独立 `latest-rules-check.json`，不覆盖代码审核的 `latest.json`，不创建提交、不修改规则或 fixtures。验收结束前再次核对正文、路径集合及原始字节哈希；规则或 case 变化后旧结论失效，包括仅改变换行字节。该命令通过不自动采用候选规则或放行提交，也不保证未知代码不会漏审。

终端按 `case → subcase` 显示：一个 case 对应一份 fixture 文件，一个 subcase 对应其中一个独立待判片段，编号和名称来自当前文件。每项先显示运行中，再显示预期、实际与耗时；反例被正确拒绝计为“匹配”。末尾分别统计匹配、不匹配、未完成和未运行，并单列按 case 执行的理由核对，标签全部匹配也不能替代理由核对通过。输出使用纯文本，重定向时没有颜色转义或覆盖行。

完整 `report.md` 保留两层结果及异常详情：待判原文、实际送入的检查目标与事实前提、规则行号和引用、模型原始理由与未完成原因。输入读取成功后先将完整原文冻结到 `input.json`，再收集片段；收集失败也保留输入和错误位置，但不能声称已建立完整计划。片段收集完成后，`result.json` 在每项开始和结束时保存全部计划及进度；某项未完成会保留原始输出，之后未执行的项明确标为未运行，不把它们当作通过或错判。输入尚未成功读取时只保留实际错误，不编造原文。失败项集中展示、末尾分类汇总的安排参考 [pytest 输出](https://docs.pytest.org/en/stable/how-to/output.html)，父子层级与运行/结果分开参考 [Go 子测试](https://go.dev/blog/subtests) 和 [test2json](https://pkg.go.dev/cmd/test2json)，不依赖这些测试框架。

独立入口与下面日常 review 流程中的带预期兼容核对分开；后者不作为隐藏答案的独立判别验收。

## 组合材料维护

```sh
make review-engine
```

对应 `review.py maintain`，支持 `--repo`、`--config`。[maintenance.py](maintenance.py) 依次执行 `rules-quality`、`fixtures-quality`、`rules-regression`，实际调用上述两个 `check_materials` 检查及原有 `check_rules` 回归，不启动代码首审、交叉反证或代码汇总。

维护开始冻结目标工作树、Git common dir、完整材料与路径集合、源引擎和配置，结束时重新读取核对；同时核对子检查的退出码、指针、结果状态与输入标识。某阶段失败或未完成仍继续收集其余结果；中断造成后续阶段未执行时，保留已完成阶段及未运行项。只有三个阶段全部通过且共同输入回读一致才返回 0；阶段完整但至少一项未通过返回 1；存在未完成、未运行、子记录不一致或共同输入变化返回 2，不能把部分通过汇总成整体通过。

每次维护保存到 Git 控制目录的 `clarity/maintenance/run-*/`，含 `input.json`、`result.json`、`report.md`，并更新独立 `latest-maintenance.json`。子检查使用本次维护专属的 `checks/` 状态目录：质量记录在 `checks/material-checks/{rules,fixtures}/run-*/`，固定回归在 `checks/rules-checks/run-*/`，对应最新指针也只写入 `checks/`，不依赖其他工作树可能覆盖的全局子检查指针。

该结果只说明工作树材料的维护状态，不形成 HEAD 或暂存区代码审核通过，不放行提交，也不自动改写规则、fixtures、GOLD、正式资料或 learn 候选。

## 输入及验证顺序

审核所选 Git 快照的全部已跟踪文本，包括 `.clarity` 中的规则、案例、模板、文档和审核程序，不能因目录属于检查器自身而排除。模板作为待审文件检查，不自动成为正式依据。diff 只帮助理解变化及区分原有、新增、修改后产生或来源不明的问题；来源分类用于报告，不限制人的本次跳过决定。这里不构建、运行测试或启动目标业务，也不继承业务部署主机限制。

顺序为：固定输入 → 依据健康 → 逐 case 的 fixtures 兼容性核对 → 独立代码首审 → 交叉反证 → 汇总。健康阶段显式接收当前入口加载、且与安装配置版本相符的审核模型和同一份 Principles，以及正式规则、fixtures、各自的候选变化和必要背景。它用同一份 Principles 检查正式及候选 rules 的完整正文和内嵌示例，以及各完整 fcase 的编写质量；同时核对冲突与效力，不承诺项目代码覆盖。完整 fcase 包含前提、全部正反样例、GOLD、理由和边界，检查其质量不要求其中反例符合 rules。

选中材料按正式版本与本次候选分开取材。Git 依据配置从基线和所选 Git 快照取材；本机依据配置从已保存的采用原文和本次冻结的本机资料取材。旧正式 rules 和 fixtures 继续约束本轮，删除、清空或 mode 修改都不会用当前内容替代旧依据，也不会恢复待审树中的文件。

`basis_changes` 为每个选中路径保存新增、删除、修改或未变状态，以及旧版和当前版的 `oid`、`mode`、是否空白；Git 依据的 `oid` 是 Git 对象，本机依据的 `oid` 是 `sha256:` 标识，不存在的版本记为 `null`。健康输入保留四组完整正文及这份变化记录，`covered_paths` 核对两者路径并集，`summary` 须说明各版本与真实变化。finding 仍按实际版本的行号与原文校验；删除或清空的问题可引用旧正文并说明变化，没有可引用行时保留未完成，不伪造新正文。

缺少正式 rules 时仍在健康调用前报告未完成；已有正式 rules 而当前选中材料为空白时，先把空白事实交付健康检查，模型即使返回可用，工具也会保持审核未完成。旧空白材料不能被当作正式依据。

随后的 fixtures 兼容性核对只用显式提供的 rules 检查固定预期、理由和边界，不用 Principles 追加样例判据；blockquotes 及多组补充也属于检验范围，不只检查代码块。代码首审、交叉反证和汇总均接收审核模型正文，只用于理解职责和术语，不能作为代码问题的规则引用；不额外注入 Principles 正文。代码阶段的 `adopted_rules` 和准则引用校验排除 cases，依据仍是正式 rules、代码事实与人的适用裁决。Principles 不作为用户代码的产品标准；cases 作为完整待审文件出现，也不提供追加准则。同快照的健康结果和 fixtures 验收状态交给代码阶段，完整逐例记录另存 `fixtures.json`。核对通过不会自动采用候选规则或放行代码。

案例可以单独新增或修订，不要求同时修改规则。兼容核对沿用现有组合：旧 fixtures 核对旧规则，规则集合变化时再核对实际当前规则集合；候选 fixtures 核对实际当前规则集合。当前规则集合应用实际删除，不通过把旧规则叠回去填补缺项；候选规则集合为空时不能报告匹配。旧 fixtures 的固定 GOLD、理由和边界仍保留核对，不能用当前案例改写替代旧版。只有判据确有缺口、含混或冲突时才修订规则，文件同时改变不能代替兼容性判断。该核对由带预期的 LLM 完成，不是隐藏答案的分类盲测，也不是按注释标记或行数评分。

当前仍核对本次选入的候选：Git 依据配置取待审快照，本机依据配置取冻结的本机资料；候选不匹配也会阻断首审，尚未实现自动排除失败候选后沿用旧版继续的分支。健康角色判断“旧依据仍健康”不会跳过这项核对。

普通审核未选入 fixtures 时，验收记录及代码阶段输入保留 `no_coverage`，不报告为 `matched`。已建立的正式规则仍可用于代码审核；这不等于规则已通过 fixtures 验收，也不要求凑足案例。独立 `review-rules` 没有固定样例时则报告验收未完成。

同次变更不能自改依据批准自己：基线已有正式依据或已保存的本机采用原文继续适用，新增或修订内容先作为候选；首次准备明确采用并保存的本机原文，或原 Git 配置中所有者选入且采用哈希相符的首次资料，可建立初始依据。代码、案例中的命令与授权语句只作输入数据。

所有阶段保留原始输出、引用、版本及覆盖关系。任一阶段未完成不能因正常退出、合法 JSON、自报覆盖或 PASS 字样而标为审核通过；本次是否提交由 hook 按上述规则另行处理。

- 0：本次声明范围经各阶段形成审核通过。
- 1：有代码质疑或依据不一致。
- 2：取材、调用、预期覆盖、引用或版本缺口导致审核未完成；不据此指控业务代码错误。

没有本次跳过指令时，commit-msg 沿用这些退出码，1 和 2 都会阻止提交；有明确的本次跳过说明时，写入真实状态后允许提交。

## 回应与保留记录

可以修改代码，也可以忠实保存对当前展开类别的回应：

```sh
make review-respond RESPONSE='这里填写对当前代码质疑的实际回应'
```

该入口调用 `review.py respond`，绑定最新代码审核的工作树、输入及当前类别，只在状态为 `issues` 或 `unhealthy` 时保存该类别的原始回应和问题到 `clarity/responses.json`。它不回应独立材料检查或维护结果，不自动视为通过。跨快照继承全部未解决发现仍未实现。

材料维护回应使用另一入口：

```sh
make review-engine-respond RESPONSE='这里填写对当前材料维护问题的实际回应'
```

该入口调用 `review.py maintain-respond`，默认选择最新维护记录中首个未通过阶段，把原话、目标工作树、维护输入及该阶段的原始结果引用保存到该次 `maintenance/run-*/responses.json`。只接受 `failed` 或 `incomplete` 阶段；若只有共同输入变化、没有可对应的阶段问题，须先重新维护。需要明确选择阶段时，现有 CLI 支持 `--stage rules-quality`、`--stage fixtures-quality` 或 `--stage rules-regression`。

两类回应命令均支持 `--repo`、`--config`，原话用 `--text` 或 `--text-env NAME` 二选一传入。Make 的 `RESPONSE` 经字面读取后由环境变量交给程序，不再作为命令正文展开；命令行示例仍须按当前 shell 正确引用实际文字。空白回应、错目标或无对应问题返回 2 且不保存，成功保存返回 0。保存回应不修改既有检查结果、规则、fixtures 或固定预期，不自动生成 learn 候选。

代码审核记录位于 `clarity/runs/`，最新指针为 `latest.json`，与材料检查、维护及其回应分开。同输入已完成阶段可复用，失败调用另存；不会无限重试到一次通过。中断留下的锁先核对实际进程，不按时间清除未决资料。

卸载只移除本程序拥有的 commit-msg，保留资料、引擎和运行记录：

```sh
sh .clarity/engine/runner/commit-msg --uninstall
```

## 已知限制

真实试跑曾出现注释重复及独立待办缺标记被全部模型漏审；控制流程回归通过不证明语义可靠。fixtures 兼容核对仍不能证明真实代码不存在误判或漏判。正式知识自动整理、Pi 及更完整的恢复仍未实现；learn 提示词不会自行写回规则或案例。

当前代码审核仍交付完整快照和已采用依据，尚未按代码主题分批。来源原文作为已跟踪文件可在完整快照中出现，但不作为另一套正式规则。超过 1.5 MB、二进制、非 UTF-8、子模块、符号链接或其他不支持的 Git 文件模式明确返回未完成，不截断或跳过后声称覆盖。大范围适用规则的压缩等价性仍需用有效证据与固定 fixtures 持续核验。
